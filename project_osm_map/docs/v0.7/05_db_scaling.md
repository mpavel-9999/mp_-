# Анализ БД: нагрузка 100 000 пользователей, статистика и партицирование

Дата: 26.10.2026. Основа — текущая схема `mp_service` (`db/mp_service.sql`, Э1–Э5), код сервера (`server/`), замеры на локальной PostgreSQL 17.6.
Статус: **анализ и предложения**; в схему ничего не внесено. Реализация — отдельным этапом по плану после согласования с владельцем.

## 1. Итог в пяти строках

1. Главный риск — **не объём таблиц, а подбор поставщиков**: `v_deal_candidates` перебирает все открытые сделки × всех поставщиков и для каждой пары вызывает `provider_can_offer` (≈ 2,6 мс на пару уже сейчас). При 25 000 поставщиков один новый запрос клиента — около минуты процессорного времени. Партицирование это не лечит; нужен предварительный отбор по индексам (сервис + гео) и хранение готового списка кандидатов.
2. Второй риск — **соединения**: сервер открывает новое соединение с БД на каждый запрос (`DriverManager`), `max_connections = 100`. Нужен пул (HikariCP) и PgBouncer.
3. **Партицировать стоит журналы**, которые только растут: `notification` (≈ 200 млн строк в год), `deal_status_log`, `rating_history`, будущие таблицы статистики. Таблицы сделки (`deal`, `deal_offer`, `deal_attribute`) — пока **нет**: 7–10 млн строк в год B-дерево держит, а партицирование `deal` ломает внешние ключи пяти таблиц.
4. **Статистику бизнеса** (финансы, прогноз цены, рейтинг, падение выручки для антифрода) не считать на лету из OLTP-таблиц, а копить в суточных агрегатах, партицированных по месяцам.
5. **Статистику планировщика** настроить явно: `pg_stat_statements`, автовакуум для горячих таблиц, `ANALYZE` родительских партицированных таблиц заданием (автовакуум их не анализирует), параметры памяти под 31,5 ГБ ОЗУ.

## 4. Что найдено в схеме

### 4.1 Подбор и вычисляемые значения (критично)

- `v_deal_candidates` — `CROSS JOIN` всех открытых сделок со всеми поставщиками и `provider_can_offer` на каждую пару. Используется в `trg_deal_status_log` (уведомления `NEW_REQUEST`), `make_auto_offers`, `Jobs` (такси — раз в минуту по всем открытым сделкам), `ProviderApi` (`GET /requests`), `DealApi` (роль `candidate`).
- Гео-условия считаются функцией `geo_distance_m` по всем строкам; PostGIS 3.5 в базе **уже установлен**, но не используется.
- `get_setting` на каждый вызов разворачивает дерево услуг рекурсивным CTE; `agent_rating` каждый раз ищет последнюю строку `rating_history`.
- `price_forecast` перебирает всех поставщиков сервиса и все закрытые сделки за 90 дней с гео-функцией на каждую строку.

### 4.2 Индексы

Нет индексов под частые условия и внешние ключи:

| Таблица | Предлагаемый индекс | Для чего |
| --- | --- | --- |
| `deal` | `(client_agent_id, deal_status_id)`, `(provider_agent_id, deal_status_id)` | «Мои сделки», `agent_pending_reviews`, `provider_busy` |
| `deal` | частичный по открытым статусам `(service_id, period_start) WHERE deal_status_id IN (MATCHING, OFFERS)` | подбор, истечение в `run_deal_jobs` |
| `deal_status_log` | `(deal_id)` | история сделки, проверка «был CONTACT» в `DealApi` |
| `notification` | `(deal_id, agent_id, notify_type_id)` | `EXISTS` в подборе такси, `CLOSING_ASK` в `run_deal_jobs` |
| `deal_review` | `(to_agent_id)` | рейтинг по отзывам |
| `agent_sanction`, `agent_subscription` | `(agent_id, …период)` | `provider_can_offer`: блокировка, подписка |
| `agent_service` | `(service_id) WHERE is_active = 1` + GiST по точке | подбор |
| `provider_slot` | GiST по точке `WHERE slot_status = 'active'` | карта клиента, подбор |
| `agent_position` | **удалить** `ix_agent_position_update` | индекс по изменяемой колонке запрещает HOT-обновления: каждое из 400 обновлений в секунду пишет и в индексы |

### 4.3 Типы и соединения

- Ключи — `numeric`, а не `bigint`: индексы больше, сравнения медленнее. Менять при первой промышленной миграции (затрагивает все таблицы и сервер).
- Новое соединение на каждый запрос (`Db.tx` → `DriverManager.getConnection`): 5–20 мс на подключение и аутентификацию, при 2 000 запросах в секунду упрётся в `max_connections = 100`. `Db.tx` задаёт параметры через `set_config(…, true)` — они живут в транзакции, поэтому совместимы с PgBouncer в режиме `transaction`.
- Параметры PostgreSQL по умолчанию: `shared_buffers = 128MB`, `work_mem = 4MB`.

## 5. Предложения

### 5.1 Подбор поставщиков (П-1, без него остальное не поможет)

1. **Гео в PostGIS.** Генерируемые колонки `geog geography(Point)` в `agent_service`, `provider_slot`, `deal`, `agent_position` и GiST-индексы; `geo_distance_m` → `ST_Distance`, условия «в радиусе» → `ST_DWithin` (использует индекс).
2. **Плоское дерево и настройки.** Таблица предков `service_ancestor(service_id, ancestor_id, depth)` и таблица действующих настроек `service_setting_effective(service_id, setting_code, rating_min, rating_max, value)` — пересобираются триггером при изменении `service` / `service_setting` (меняются редко). `get_setting` и `service_covers` читают их по ключу.
3. **Текущий рейтинг.** Колонка или таблица `agent_rating_current(agent_id, role_id, service_id, rating)`, обновляется при записи `rating_history`; `agent_rating` без даты читает её.
4. **Отбор в два этапа.** Сначала дешёвые индексные условия — сервис покрывается (`service_ancestor`), поставщик в радиусе (`ST_DWithin`), активная роль, подписка, нет блокировки; затем `provider_can_offer` только для короткого списка (десятки, а не 25 000).
5. **Кандидаты хранятся.** Таблица `deal_candidate(deal_id, provider_agent_id, date_creation, is_skipped)` заполняется один раз при переходе в MATCHING (там же уведомления и автоотклики); при новой публикации или смене зоны поставщика — дозаполняется по его открытым сделкам. `GET /requests` читает таблицу; правильность всё равно гарантирует повторная проверка в `trg_deal_offer_check`. Строки удаляются вместе с закрытием сделки (или партиция по дате).

Оценка: новый запрос — десятки миллисекунд вместо минуты; `GET /requests` — один индексный запрос.

### 5.2 Соединения и параметры сервера (П-1)

- Сервер: пул HikariCP (20–40 соединений), `Db.tx` берёт соединение из пула.
- PgBouncer в режиме `transaction` перед PostgreSQL, если серверов API будет несколько.
- PostgreSQL на машине 31,5 ГБ (если БД — основной потребитель): `shared_buffers = 8GB`, `effective_cache_size = 20GB`, `work_mem = 16MB`, `maintenance_work_mem = 1GB`, `random_page_cost = 1.1` (SSD), `max_wal_size = 4GB`, `checkpoint_completion_target = 0.9`. Для прототипа на одной машине с эмуляторами — вдвое меньше.
- Уведомления: при росте — длинный опрос или SSE вместо опроса раз в 2–5 с (снизит 2 000 запросов в секунду в разы).

### 5.3 Партицирование (П-2)

| Таблица | Партицировать? | Как | Почему |
| --- | --- | --- | --- |
| `notification` | **Да** | `RANGE (date_creation)` по месяцам; ключ `(notification_id, date_creation)`; хранить 6–12 месяцев, старые партиции — архив и `DROP` | Самая большая таблица; чтение — только свежие строки; удаление старого — `DROP PARTITION` вместо `DELETE` и вакуума. В запрос опроса добавить `date_creation > now() - interval '2 days'`, чтобы работало отсечение партиций |
| `deal_status_log` | **Да** | `RANGE (date_creation)` по месяцам | Только вставка; отчёты по периодам; архив |
| `rating_history` | **Да** (или меньше писать) | `RANGE (rating_date)` по годам; писать строку только при изменении рейтинга | До 73 млн строк в год при ежедневной записи |
| Таблицы статистики (5.4) | **Да** | `RANGE (stat_date)` по месяцам | Растут по дням, читаются по периодам |
| `deal_candidate` (5.1) | Да, если не удалять сразу | `RANGE (date_creation)` по неделям | Миллионы строк в день при широком подборе; `DROP` старых недель |
| `deal`, `deal_offer`, `deal_attribute`, `deal_review` | **Пока нет** | При > 50–100 млн сделок — `RANGE (date_creation)` по кварталам, ключ `(deal_id, date_creation)` во всех ссылающихся таблицах | 7 млн строк в год — норма для B-дерева; на `deal` ссылаются 5 таблиц, ключ пришлось бы менять везде. Горячие открытые сделки обслуживают частичные индексы |
| `agent_position` | **Нет** | `fillfactor = 70`, удалить индекс по `date_update`; возможно `UNLOGGED` (положение не жалко потерять при сбое) | Одна строка на агента; проблема в частоте обновлений, а не в объёме |
| `provider_slot` | Нет | частичные индексы по `active`; закончившиеся окна — в архив раз в сутки | Активных строк мало |

Особенности PostgreSQL 17, которые надо учесть:
- первичный и уникальные ключи партицированной таблицы обязаны включать ключ партицирования;
- внешний ключ **на** партицированную таблицу допустим, но тоже должен включать ключ партицирования — поэтому `notification` и журналы удобны (на них никто не ссылается), а `deal` — нет;
- автовакуум **не анализирует родительскую** партицированную таблицу — нужен `ANALYZE` родителя плановым заданием;
- партиции на будущее создаёт задание (сервер раз в сутки: «создать партицию следующего месяца, если нет») или `pg_partman`, если его установят (сейчас в списке доступных расширений нет).

### 5.4 Сбор статистики бизнеса (П-2)

Сейчас `v_agent_finance_daily` и `v_company_finance_daily` — обычные представления, агрегируют все сделки при каждом чтении; `price_forecast` перебирает сделки за 90 дней. Предложение — суточные агрегаты:

| Таблица | Поля | Кто заполняет | Для чего |
| --- | --- | --- | --- |
| `stat_agent_daily` | `stat_date, agent_id, role_id, service_id, deals_closed, deals_cancelled, cancel_penalty, income, expense, reviews_sum, reviews_cnt` | Триггер на финальный статус сделки (`UPSERT` за день) + сверка ночным заданием | Финансы агента и компании, рейтинг, падение выручки для антифрода (`register_fraud_episode`) |
| `stat_price_cell` | `stat_date, service_id, cell_id (сетка forecast_grid_m или geohash), deals, price_sum, price_min, price_max, median` | Ночное задание по закрытым за день сделкам | `price_forecast` — 90 строк ячейки вместо перебора сделок |
| `stat_service_daily` | `stat_date, service_id, requests, offers, agreed, closed, expired, cancelled, avg_offers, avg_time_to_agree` | Ночное задание | Отчёты платформы, спрос и предложение (алгоритм, раздел 8) |
| `rating_history` | как сейчас, но только при изменении | Задание пересчёта рейтинга | История рейтинга |

Все — `RANGE` по `stat_date` помесячно, `COMMENT ON` на каждое поле (правило проекта). Представления `v_*_finance_daily` переписываются поверх агрегатов — приложение и API не меняются.

### 5.5 Статистика планировщика и наблюдение (П-2)

- Установить `pg_stat_statements` (доступно) и `auto_explain` для запросов дольше 200 мс; `log_min_duration_statement = 500ms`.
- Автовакуум для горячих таблиц: `agent_position` — `autovacuum_vacuum_scale_factor = 0.01`; `deal`, `deal_offer` — `0.02`; журналы (`notification`, `deal_status_log`) — `autovacuum_vacuum_insert_scale_factor = 0.05`, чтобы карта видимости обновлялась и работал index-only scan.
- Расширенная статистика: `CREATE STATISTICS` на `deal (service_id, deal_status_id)` и `agent_service (service_id, is_active)` — колонки зависимы, без неё планировщик ошибается в оценках строк.
- Для неравномерных колонок (`service_id`, статусы) — `ALTER COLUMN … SET STATISTICS 500`.
- `ANALYZE` родительских партицированных таблиц раз в сутки (задание сервера).
