# План этапа Э4 — экраны клиента

Основа: [01_deal_algorithm.md](../01_deal_algorithm.md) разделы 1, 3 (п. 1, 4, 5.2–5.6), 7; [03_implementation_spec.md](../03_implementation_spec.md) 4.4, 4.6, 4.7, 5.3, 5.4; [04_product_architecture.md](../04_product_architecture.md) 6.1, 8; итог Э3 — [E3_app.md](E3_app.md); решение Р-3 — все сервисы показываются всем.
Результат: клиент на эмуляторе проходит путь «услуга → запрос → отклики → согласование → сделка → отмена или баллы» в трёх раскладках A/B/C. Правила процесса остаются в БД: экран показывает только действия из `Deal.actions`.

## Принципы

1. **Правила — на сервере.** Кнопки сделки строятся только из `Deal.actions`. Платна ли отмена, приложение не вычисляет: БД отдаёт `cancel_mode` (шаг 1).
2. **Одна логика — три раскладки** (как в Э3): у экрана одна `ViewModel`, шаблон выбирает только composable по `template.screens`: `deal_form` (запрос) — `sheet` / `wizard` / `form_rows`; `offers` — `map_sheet` / `cards_toggle` / `map_table`; `deal` — `sheet_timeline` / `cards_timeline` / `dense_rows`. Баллы, отмена, «Мои сделки» — общие для всех шаблонов (ТЗ 5.3).
3. **Тексты — из глоссария.** Недостающие термины добавляются в БД, а не в код. Ошибки API показываются по коду: термин `ui.err.<код строчными буквами>` (`REVIEW_REQUIRED` → `ui.err.review_required`), если он есть, иначе — текст сервера.
4. **Свежие данные без лишних запросов.** Один опрос `GET /notifications?since=` на всё приложение: раз в 2 с, пока открыт экран сделки, иначе раз в 5 с (ТЗ 4.7). Экран сделки перечитывает сделку, только когда пришло уведомление по ней. Старые уведомления при входе не показываются: первый опрос лишь запоминает последний номер.

## Проверка связности

- **Порядок.** БД (1) нужна API (2); API — экрану сделки (6). Основа (3) — всем экранам. Главная (4) открывает запрос (5), запрос создаёт сделку (6), сделка ведёт к баллам (7). Список сделок (8) использует экран сделки (6). Каждый шаг опирается только на уже сделанное.
- **Алгоритм.** Создание запроса — п. 1.1–1.10 (включая запрет без баллов — проверяет сервер, `REVIEW_REQUIRED`). Отклики и согласование — п. 4.1–4.5: порядок и смещение точек считает БД (`v_deal_offer_list`), приложение их только показывает. Сближение (п. 4.6) задаёт сервер; на экране видно, как статус меняется на CONTACT и открываются поля `show_stage = near`. Отмена — п. 5.2–5.4: итог решает `deal_cancel`, экран заранее показывает `cancel_mode` из той же функции. Баллы — п. 5.6.
- **Шаблоны.** Ключи раскладок взяты из `UI_TEMPLATE.screens` в БД: `deal_form`, `offers`, `deal` — для каждого шаблона по одному значению; новые ключи не нужны.
- **Данные.** Поля формы запроса в тестовых данных — `text`, `number`, `address`; остальные типы поддерживаются заранее, чтобы новый сервис добавлялся только данными. Публикация на карте может быть на уровне сервиса (`service_id = 100`) — тогда в запросе выбирается вариант (п. 1.1: сделка создаётся на варианте).
- **Доступ.** Р-3: главная показывает все сервисы. Создать запрос сервер разрешит только по доступному сервису; у `user_testing_1…5` доступ ко всем, у агента 2 — к части. Отказ — текст `ui.err.no_service_access`.
- **Безопасность.** Точное место и имя поставщика до согласования не приходят из API — приложение не может их показать по ошибке. Ссылки на маршрут приходят только после согласования.
- **Тестовые данные для сценариев.** Кейс A/B/C/D — сделка 6 (парковка 1001, радиус 100 м) и сделка 7 (такси 1101) клиента агента 1; начало периода — через 2 ч от загрузки БД, поэтому после перезагрузки они снова открыты для откликов. Агент 1 входит только по `agent_id` (`MP_DEV_LOGIN=1`). Для S-11 создаётся запрос с началом через 5 мин — плановое задание сервера переведёт его в EXPIRED.
- **Перезагрузка БД.** Новая функция и тексты появляются только после загрузки `mp_service.sql`, а он пересоздаёт схему: сделки, созданные проверками Э2–Э3, пропадут, тестовые данные (кейс A/B/C/D) вернутся в исходное состояние.

- **Часовой пояс (вопрос владельцу).** API передаёт время без пояса (ТЗ 4), сервер живёт по времени Алматы. Эмулятор по умолчанию в UTC: запрос «с 15:30» по телефону для сервера уже в прошлом и сразу истекает. Для проверки на эмуляторе выставлен пояс `Asia/Almaty` (`adb shell cmd alarm set-timezone Asia/Almaty`). Предложение: сервер отклоняет запрос с началом в прошлом (понятная ошибка), а позже время передаётся со смещением (`+05:00`).
- Отклик водителя такси показывает «0 м · примерно»: для маршрутных сервисов смещение точки нулевое — пометку «примерно» для них стоит убрать (Э5, вместе с экраном отклика).
- Тексты ошибок сервера без термина `ui.err.*` по-прежнему только по-русски; заведено 8 основных кодов.
- SQL-тесты опираются на исходное состояние кейса A/B/C/D (сделка 6): после ручной проверки их нужно запускать на свежезагруженной БД.
