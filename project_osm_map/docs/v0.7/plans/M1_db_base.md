# План этапа М1 — масштабирование БД: основа и замеры

Основа: [05_db_scaling.md](../05_db_scaling.md) — решение владельца, разделы 2 (модель нагрузки), 3 (замеры), 4.2–4.3 (индексы, типы, соединения), 5.2 (пул и параметры), 5.3 (`agent_position`), 5.5 (наблюдение и автовакуум), 6 (порядок работ); [03_implementation_spec.md](../03_implementation_spec.md), раздел 3 «М1–М3»; итог Э6 — [E6_close.md](E6_close.md).
Результат: есть воспроизводимый нагрузочный стенд (100 000 агентов, 25 000 поставщиков, 1 млн сделок) и замер горячих запросов «как есть»; сервер берёт соединения из пула; в схеме — недостающие индексы, `agent_position` без индекса по `date_update` и с `fillfactor`, ключи `bigint`; PostgreSQL настроен под машину, включены `pg_stat_statements` и автовакуум горячих таблиц. Таблица замеров «до / после» — в этом плане. Поведение API и приложения не меняется.

## Что уже есть (из Э1–Э6)

- **БД:** `db/mp_service.sql` (3 440 строк) пересоздаёт схему `mp_service` целиком; 30 таблиц, ключи и внешние ключи — `numeric` (≈ 216 упоминаний `numeric`, из них часть — координаты `numeric(9,6)`, деньги `numeric(12,2)`, рейтинги `numeric(3,2)` — они не меняются); 25 параметров функций и 11 результатов `numeric` / `numeric[]` по номерам; последовательности `deal_seq`, `deal_offer_seq` и др. (уже `bigint`). Индексов 7, в том числе `ix_agent_position_update` (мешает HOT-обновлению). Расширения — только `pgcrypto`; PostGIS установлен, но не используется (это М2).
- **Сервер:** `Db.tx` открывает соединение на каждый запрос через `DriverManager.getConnection`; параметры сессии (`search_path`, `TimeZone`, `mp.agent_id`, `mp.geo_secret`) задаются `set_config(…, true)` — живут в транзакции, совместимы с пулом. HTTP — `Executors.newFixedThreadPool(8)`; плановое задание `Jobs` — отдельный поток. В SQL сервера ≈ 50 приведений `?::numeric` — часть по номерам (`service_id`, язык, `agent_id`), часть по координатам.
- **Приложение:** номера в моделях и маршрутах — `Long`; JSON отдаёт номера числами — смена типа в БД ответ не меняет.
- **PostgreSQL 17.6:** параметры по умолчанию (`shared_buffers = 128MB`, `work_mem = 4MB`, `max_connections = 100`, `shared_preload_libraries` пусто).
- **Тесты:** SQL `01_rules` 30, `02_cancel_mode` 5, `03_period` 5, `04_close` 8; `api_smoke.py` 19; JVM (приложение) 39.

## Принципы

1. **Поведение не меняется.** Ответы API, правила сделки, тексты и экраны — прежние; доказательство — те же SQL-тесты, `api_smoke.py` и JVM-тесты зелёные после каждого шага, меняющего схему или сервер.
2. **Стенд отделён от схемы.** Код генератора и результаты замеров — в схеме `mp_load` (файл `db/load/mp_load.sql`, загружается после `mp_service.sql`); сгенерированные строки — в таблицах `mp_service` (замеряем настоящие запросы), номера с 1 000 000, чтобы не пересечься с кейсом A/B/C/D. Тесты гоняются на свежезагруженной схеме без нагрузки — они опираются на кейс A/B/C/D.
3. **Повторяемость.** Генератор детерминирован (`setseed`), объёмы — параметрами; «до» и «после» замеряются на одинаковых данных. Каждый шаг, меняющий схему, — перезагрузка `mp_service.sql`, `mp_load.sql`, генерация, `ANALYZE`, замер.
4. **Генератор вне правил.** Строки вставляются напрямую в итоговых статусах (`session_replication_role = replica` — триггеры и проверки внешних ключей отключены на время вставки), иначе миллион сделок шёл бы через подбор по минуте на запрос. Поэтому после вставки — своя проверка целостности (`mp_load.check()`: сироты по всем внешним ключам, допустимые статусы, суммы) — ноль нарушений.
5. **Замер — двумя способами.** SQL (`mp_load.bench`): каждый горячий запрос N раз со случайными параметрами из сгенерированных данных, медиана и 95-й процентиль, планы `EXPLAIN (ANALYZE, BUFFERS)`. HTTP (`server/tests/load_http.py`): параллельные клиенты через вход по `agent_id` (`MP_DEV_LOGIN=1`, паролей не нужно), медиана, 95-й процентиль, запросов в секунду — только так виден эффект пула.
6. **Правила БД проекта.** Все новые таблицы, поля и функции `mp_load` — с `COMMENT ON`, в теле функций — методика; после загрузки проверка по `pg_attribute` (`relkind IN ('r','v','m')`) — без пропусков, в том числе для `mp_load`.
7. **Ресурсы.** Тяжёлое — по одному: генерация, замер, сборка, сервер — никогда одновременно; эмуляторы в М1 не запускаются (В-М1-5). Перед генерацией — проверка ОЗУ (≥ 6 ГБ), C: (≥ 20 ГБ, стенд ≈ 5–10 ГБ), ЦП (< 80 %). Долгие команды — в фоне. После шага — сервер и демоны Gradle остановлены.

## Проверка связности

- **Порядок.** Генератор (1) — первым: без данных нечего замерять. Замер «как есть» (2) — до любых изменений, иначе нет «до». Пул (3) не трогает схему — его эффект виден на тех же данных без перезагрузки. Индексы (4) и `bigint` (5) меняют `mp_service.sql` — каждый со своей перезагрузкой и генерацией, чтобы эффект каждого был виден отдельно и ошибка искалась в одном изменении; индексы раньше `bigint`, потому что они нужнее и проще, а `bigint` затем пересоздаёт их уже с новым типом. Параметры (6) — последними: они ускоряют всё сразу и смешали бы эффекты шагов 3–5. Итог (7) — на всём вместе. Каждый шаг опирается только на сделанное раньше.
- **Алгоритм и ТЗ.** Правила сделки, переходы, тексты, `Deal.actions` не меняются — меняются только типы, индексы, способ получения соединения и параметры сервера БД. Поведение доказывают прежние тесты; новых правил в М1 нет. Состав М1 — ровно раздел 3 ТЗ; то, что в 05 относится к подбору и журналам, оставлено М2 и М3 (границы выше).
- **Пул и параметры сессии.** `mp.agent_id` и `mp.geo_secret` задаются на транзакцию (`set_config(…, true)`), поэтому соединение из пула не «помнит» чужого агента; `deal_contact_check` переключается на систему и восстанавливает агента внутри той же транзакции (Э6) — с пулом так же. `TimeZone` тоже транзакционный — пояс Алматы (Р-4) сохраняется.
- **`bigint` и приложение.** Номера в JSON — целые числа и при `numeric`, и при `bigint`; в приложении они `Long` — изменений не ожидается, проверка — JVM-тесты и `api_smoke.py`. Опасное место — вызовы функций с `?::numeric` у номеров: после смены параметров на `bigint` PostgreSQL не найдёт функцию (`numeric` в `bigint` неявно не приводится) — поэтому сервер меняется в том же шаге, и `api_smoke.py` это ловит.
- **Генератор и правила.** Вставка в обход триггеров не проверяет правила — поэтому `mp_load.check()`, а сами правила по-прежнему проверяют SQL-тесты на чистой схеме. Сгенерированные сделки в итоговых статусах не порождают уведомлений и заданий; открытые (300 + 2 000) — согласованы по статусам, сторонам и откликам, чтобы `run_deal_jobs` и `deal_contact_check` работали на них как на настоящих.
- **Перезагрузки БД.** Шаги 1, 4, 5, 7 пересоздают схему — данные ручных проверок пропадают, кейс A/B/C/D возвращается в исходное состояние. Перед первой — дамп (шаг 0). `pg_stat_statements` живёт в `public` и пересоздание `mp_service` переживает.
- **Безопасность.** Пароли — только в переменных окружения команд; генератор не создаёт паролей (вход на стенде — по `agent_id` в режиме `MP_DEV_LOGIN=1`, только локально).
