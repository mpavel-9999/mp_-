# План этапа Э2 — API v0.7

Основа: [03_implementation_spec.md](../03_implementation_spec.md) раздел 4 (методы) и 6 (код закрытия), [02_db_architecture.md](../02_db_architecture.md) разделы 6.3 и 8, итог Э1 — [E1_db.md](E1_db.md).
Результат: сервер `project_osm_map/server/` отдаёт все методы v0.7 поверх схемы `mp_service` v0.7, правила процесса остаются в БД.

## Принципы

1. **Правила — в БД.** Сервер не решает, можно ли откликнуться, согласовать или отменить: он вызывает функции БД (`provider_can_offer`, `deal_agree`, `deal_cancel`, `run_deal_jobs`, `make_auto_offers`) и переводит их ошибки в HTTP-ответы. На сервере — только то, что БД сделать не может: сессии, код закрытия (HMAC), маршруты по дорогам (GraphHopper), плановые задания.
2. **JSON собирает и разбирает PostgreSQL**, как в v0.6: ответы — `json_agg` / `row_to_json`, тело запроса передаётся параметром `?::jsonb` и разбирается в SQL. Внешних JSON-библиотек на сервере нет.
3. **Сессия БД на запрос:** соединение, `set_config('mp.agent_id', …)`, `set_config('mp.geo_secret', …)`, транзакция, коммит/откат. Тогда триггеры знают автора действия, а смещение точек — секрет.
4. **Ошибки:** `{"error": "текст", "code": "КОД"}`. Код берётся из `HINT` исключения БД (`OWN_DEAL`, `BUSY`, `PRICE_OUT_OF_RANGE` …) или задаётся сервером (`UNAUTHORIZED`, `NOT_FOUND`, `CODE_EXPIRED`). 400 — неверный запрос, 401 — нет сессии, 403 — нет прав, 404 — нет объекта, 409 — нарушено правило процесса, 422 — неверный код закрытия.

## Проверка связности

- **Доступность данных.** Каждый метод опирается на объекты Э1: представления (`v_deal_offer_list`, `v_deal_candidates`, `v_provider_slot_map`, `v_ui_options`, `v_map_cursor`) и функции (`agent_login_check`, `deal_agree`, `deal_cancel`, `make_auto_offers`, `price_forecast`, `run_deal_jobs`). Нового правила на сервере не появляется.
- **Порядок.** Каркас и сессии (1, 2) нужны всем методам. Маршрутизация (5) — до клиента и поставщика, потому что такси в обоих. Закрытие (8) — после сделок (6), секрет создаёт БД при согласовании.
- **Такси.** БД не проверяет маршрут (`provider_can_offer` для `route` пропускает гео). Поэтому для маршрутных сервисов сервер сам фильтрует кандидатов по маршруту, шлёт `NEW_REQUEST` и создаёт автоотклики с ценой `max(порог, цена за км × длина)`. Для остальных сервисов это делает БД. Двойной рассылки нет: триггер БД пропускает `route`.
- **Безопасность.** Пароль проверяет БД, на сервере хранятся только токены в памяти. Код закрытия выдаётся только поставщику сделки; секрет сделки в ответы не попадает (в `GET /deals/{id}` поле `close_secret` не выбирается). Точная точка и имя поставщика — только через представления, которые сами учитывают статус.
- **Совместимость с приложением v0.6.** Старое приложение на эмуляторах перестанет работать после Э2 — это ожидаемо: оно переписывается в Э3–Э6.
- **Зависимость.** GraphHopper (Maven Central) — единственная новая библиотека сервера; импорт графа Казахстана при первом запуске займёт несколько минут и около 1–2 ГБ памяти, кэш сохраняется в `server/data/gh-cache` (в `.gitignore`).
- **Открытый момент.** Вход по `agent_id` для агентов 1–6 (кейс A/B/C/D) остаётся только в режиме разработки (`MP_DEV_LOGIN=1`) — у них нет логинов. Если нужно, заведу им логины позже.
