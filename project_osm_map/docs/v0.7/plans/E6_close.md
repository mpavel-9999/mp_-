# План этапа Э6 — режим тестирования, положение и закрытие сделки

Основа: [01_deal_algorithm.md](../01_deal_algorithm.md) разделы 2 (переходы AGREED → CONTACT → CLOSED, AGREED → CLOSED для `online`), 3 (п. 5.1–5.1.4, 5.5, 5.6), 5 (режим тестирования), 7 (S-4…S-8); [03_implementation_spec.md](../03_implementation_spec.md) 4.3, 4.6, 4.7, 5.3 («Код закрытия», «Подтверждение»), 5.4, 5.5, 6; итог Э5 — [E5_provider.md](E5_provider.md).
Результат: стороны согласованной сделки видят друг друга на карте; в режиме тестирования агент перетаскивает свой курсор, в обычном — положение берётся с GPS; при сближении сделка переходит в CONTACT; клиент и поставщик закрывают сделку кодом (QR или цифры), в режиме тестирования — «Сканировать QR» и «Предоставить QR» без камеры; после закрытия обе стороны ставят баллы. Всё — в раскладках A/B/C, экраны кода и подтверждения — общие.

## Что уже есть (из Э1–Э5)

- **БД:** `agent_position` и триггер `trg_agent_position_check` (`manual` — только `is_testing`); переход в CONTACT — в `run_deal_jobs` (раз в минуту, свежесть положения `position_ttl_s` = 120 с, радиус `near_radius_m`); `close_secret` при AGREED; переход AGREED → CLOSED для гео-услуг отклоняется (`RAISE` без кода); уведомления `NEAR`, `CLOSE_REQUEST`, `CLOSE_CODE`, `CLOSING_ASK`, `REVIEW_REQUIRED`; курсоры `MAP_CURSOR`.
- **API:** `PUT /me/position`, `GET /deals/{id}/positions`, `close/request`, `close/code` (`expires_in_s`, а не `expires_at`, как в ТЗ 4.6), `close`, `close/test-scan`, `close/test-provide`; действия `close`, `show_code`, `enter_code`, `test_scan`, `test_provide` в `Deal.actions`. `api_smoke.py` проходит сближение курсорами, QR, неверный код, `test-provide`.
- **Приложение:** методы репозитория для всех запросов закрытия и положения; на экране сделки — курсоры сторон из `/deals/{id}/positions` (опрос 5 с). Кнопок закрытия, экранов кода и подтверждения, GPS и перетаскивания нет; разрешения на геолокацию нет.

## Принципы

1. **Правила — в БД и на сервере** (как в Э3–Э5). Когда сделка в CONTACT, решает БД по свежим положениям; можно ли закрыть, показать код или сканировать — `Deal.actions`. Приложение показывает кнопки только по действиям: `close` — «Закрыть сделку», `show_code` — «Показать код», `enter_code` — «Ввести код», `test_scan` — «Сканировать QR», `test_provide` — «Предоставить QR».
2. **Код считает только сервер.** Приложение не знает `close_secret`; поставщик берёт код через `GET /close/code` и обновляет его по `expires_in_s`; клиент отправляет цифры или `qr_payload` как есть.
3. **Положение по режиму агента.** `is_testing` — только курсор (`source = manual`), GPS не запрашивается; обычный агент — только GPS (`source = gps`, `manual` сервер отклонит). На экране согласованной сделки (AGREED / CONTACT) приложение отправляет положение раз в 10 с; в режиме тестирования — последнюю точку курсора, чтобы она не устарела (`position_ttl_s` = 120 с).
4. **Общие экраны.** «Код закрытия» и «Подтверждение» — общие для шаблонов (ТЗ 5.3); кнопки закрытия — в общем блоке `DealActionsRow`, поэтому появляются во всех раскладках сделки A/B/C. Новых ключей `UI_TEMPLATE.screens` нет.
5. **Тексты — из глоссария.** Новые термины — в БД (номера 50150+), RUS и ENG; ошибки — `ui.err.<код>`.
6. **Свежие данные — по уведомлениям** (один опрос из Э4): `CLOSE_REQUEST` открывает поставщику экран кода, `CLOSE_CODE` — автоподтверждение у тестового клиента, `NEAR` и `REVIEW_REQUIRED` обновляют сделку и ведут к баллам, `CLOSING_ASK` — снекбар «Закрыть сделку».

## Проверка связности

- **Порядок.** БД (1) — первой: от `deal_contact_check` и HINT `CONTACT_REQUIRED` зависят API (2) и проверки S-4, S-7. Основа приложения (3) — после API, потому что модели берутся из ответов шага 2. Положение (4) нужно закрытию гео-сделок (5): без CONTACT действий `enter_code` и `test_scan` нет. Автоподтверждение и выбор из списка (6) используют экраны шага 5; онлайн-услуга (7) — тот же экран кода без положения. Каждый шаг опирается только на сделанное раньше.
- **Алгоритм.** Переход в CONTACT — только БД (`deal_contact_check` от имени системы, как в `DEAL_TRANSITION`: AGREED → CONTACT выполняет `system`); плановое задание остаётся запасным путём. Закрытие — только клиент и только по действующему коду текущего или предыдущего интервала (ТЗ 6); для гео-услуги — из CONTACT, для `online` — из AGREED (триггер). Баллы после CLOSED обязательны — БД (`REVIEW_REQUIRED`), экран баллов из Э4.
- **Режим тестирования.** `manual` принимает только триггер для `is_testing`; `test-scan` и `test-provide` — только `is_testing` (сервер, `NOT_TESTING`); автоподтверждение `CLOSE_CODE` — только у тестового клиента (ТЗ 6). Обычный агент видит и делает то же, что без режима тестирования (алгоритм, раздел 5).
- **Положение и время.** Свежесть положения — `position_ttl_s` (120 с) в БД; отправка раз в 10 с держит положение свежим и в режиме тестирования. Расчёт кода — по unix-времени сервера, пояс Алматы (Р-4) на него не влияет.
- **Безопасность.** `close_secret` не уходит из БД и сервера; положения отдаются только сторонам согласованной сделки; поля `show_stage = near` открывает сервер после CONTACT — приложение ничего не открывает само. Код в уведомлении `CLOSE_CODE` получает только клиент сделки.
- **Перезагрузка БД.** Шаг 1 меняет `mp_service.sql` — схема пересоздаётся, данные ручных проверок пропадут, кейс A/B/C/D вернётся в исходное состояние. Перед перезагрузкой — дамп (шаг 0).
