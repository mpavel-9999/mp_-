# План этапа Э5 — экраны поставщика

Основа: [01_deal_algorithm.md](../01_deal_algorithm.md) разделы 2, 3 (п. 2.1–2.10, 3.1–3.5, 4.4, 5.2–5.6), 4.1–4.3, 7; [03_implementation_spec.md](../03_implementation_spec.md) 4, 4.5, 4.7, 5.3, 5.4; [04_product_architecture.md](../04_product_architecture.md) 6.1, 6.4; итог Э4 — [E4_client.md](E4_client.md); решение Р-4 — время в API алматинское.
Результат: поставщик на втором эмуляторе публикует место или маршрут, получает подходящие запросы, откликается и ведёт согласованную сделку до отмены или баллов в трёх раскладках A/B/C. Клиент на первом эмуляторе — экраны Э4. Время запросов и публикаций не зависит от часового пояса устройства.

## Принципы

1. **Правила — в БД** (как в Э3–Э4). Можно ли откликнуться, решает `provider_can_offer`: приложение показывает «Откликнуться» только по действию `offer` из `Deal.actions` или для запроса из `GET /requests`; отказ — по коду `ui.err.*`.
2. **Одна логика — три раскладки.** Входящие запросы — существующий ключ шаблона `provider_request` (`sheet` / `cards` / `dense`). Публикация — новый ключ `slot_form` (`sheet` / `wizard` / `form_rows`, по образцу `deal_form`). Список публикаций и настройки сервиса — общие для всех шаблонов (ТЗ 5.3).
3. **Тексты — из глоссария.** Новые термины — в БД (номера 50115+), RUS и ENG.
4. **Время — алматинское всюду.** Сервер и БД считают «сейчас» в `Asia/Almaty`; приложение берёт «сейчас» и показывает время по Алматы, не по поясу устройства. Строки времени в API остаются без смещения (ТЗ 4).
5. **Свежие данные — по уведомлениям** (один опрос из Э4): `NEW_REQUEST` обновляет список входящих запросов, `AGREED` / `CANCELLED` — экран сделки и «Мои сделки».

## Проверка связности

- **Порядок.** Время (1) — первым: от него зависят проверки периода во всех следующих шагах и сценарий S-11 на эмуляторе в UTC. Тексты и ключ шаблона (2) нужны экранам 5–9; API (3) — экранам 7–8. Основа (4) — всем экранам. Раздел (5) открывает публикацию (6), входящие (7) и настройки (9); отклик (7) ведёт в сделку (8). Каждый шаг опирается только на сделанное раньше.
- **Алгоритм.** Подбор п. 2.1–2.9 — только `provider_can_offer` и проверка маршрута сервера (`matchingDealsFor`); приложение ничего не фильтрует, кроме «Пропустить» (личное скрытие, не правило). Автоотклик п. 3.1 — БД (`make_auto_offers`), экран только включает `is_auto`. Ручной отклик п. 3.2–3.5 — триггер повторно проверяет условия. Согласование п. 4.4 (declined / withdrawn) — БД; экран поставщика это только показывает. Отмена и баллы — общие экраны Э4 с `cancel_mode`.
- **Время.** Сравнения с `now()` — в БД (`run_deal_jobs`, `EXPIRED`, новые проверки периода) и на сервере; с поясом сессии `Asia/Almaty` `now()::timestamp` совпадает с временем строк API. Сейчас в PostgreSQL пояс `Asia/Tashkent` (тоже UTC+5) — поведение не меняется, меняется только явность. Проверка `PERIOD_IN_PAST` применяется только к вставкам от агента: тестовые данные и прошлые сделки загружаются без `mp.agent_id`; запас 1 мин — на задержку между формой и отправкой.
- **Шаблоны.** `provider_request` уже есть в `UI_TEMPLATE.screens`; `slot_form` добавляется данными в БД, код раскладок выбирается по нему так же, как `deal_form`.
- **Доступ и роли.** Вкладка «Поставщик» — по ролям из `/me`; публиковать можно только подключённый сервис с подпиской (сервер, `NO_SERVICE_ACCESS`). Роль в сделке (`candidate` / `offerer` / `provider`) задаёт сервер.
- **Безопасность.** Поставщик до согласования видит точку и зону запроса клиента (нужно для решения, п. 3.3), но не имя и не поля `show_stage = agreed/near` — так отдаёт API; приложение ничего не открывает само.
- **Перезагрузка БД.** Шаги 1–2 меняют `mp_service.sql` — он пересоздаёт схему: сделки ручных проверок пропадут, кейс A/B/C/D вернётся в исходное состояние. Перед перезагрузкой — дамп (шаг 0).
