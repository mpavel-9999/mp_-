# ТЗ: платформа-маркетплейс услуг

Версия 0.6 от 24.10.2026. Источник: документ «ТЗ: платформа-маркетплейс услуг» в Claude Docs. Структура БД и тестовые данные — в `mp_service.sql` (PostgreSQL 15+).

Платформа, где агенты предоставляют и получают услуги: 10 сервисов в 5 категориях, от парковки до репетитора. Модель данных упрощена до 27 таблиц в схеме mp_service, и новый сервис добавляется только данными. Все 19 вопросов версии 0.5 решены; 5 новых вопросов — в первом разделе (ОВ-20…ОВ-24).

## Цель и модель монетизации

Нужна гибкая модульная платформа, где новый сервис добавляется данными, без изменения кода. Интерфейс клиента строится из файла конфигурации и обновляется без выпуска новой версии приложения.

- Новые сервисы, их атрибуты, языки, пакеты, тарифы, порядок вывода откликов и ссылки на карты добавляются записями в справочниках.
- Одна модель данных подходит для всех сервисов: справочники, связки, факты.

Монетизация на первом этапе:

1. Ознакомительный период от 1 до 3 месяцев (ОВ-2).
2. Абонплата за пакет сервисов (ОВ-7).
3. Реферальное вознаграждение: процент от абонплаты привлечённых агентов, зависит от уровня вложенности (ОВ-3, ОВ-4, ОВ-5).

Сбор с каждой сделки пока выключен. Его можно включить настройкой deal_fee_percent без изменения структуры.

## Основные понятия

| Понятие | Описание |
| --- | --- |
| Агент | Пользователь платформы. Одна учётная запись может иметь несколько ролей и сервисов. |
| Роль | Клиент, Поставщик услуг, Компания (объединяет агентов), Субагент (входит в компанию). |
| Сервис | Узел дерева услуг: категория, сервис или вариант (Красота → Парикмахерская → Мужская стрижка). Отдельно есть «Базовый профиль», общий для всех. |
| Пакет сервисов | Набор сервисов за абонплату для одной роли. Для компании в пакет входит N субагентов, следующие оплачиваются отдельно. |
| Ознакомительный период | Бесплатный доступ к пакету на 30–90 дней. Даётся агенту один раз. |
| Реферал | Агент, приглашённый другим агентом. Пригласивший получает процент от его оплаченной абонплаты. |
| Атрибут | Поле карточки: ФИО, псевдоним, телефон, гос. номер. Бывает группой, справочником или значением справочника. |
| Сделка | Запрос клиента на услугу с точкой, радиусом зоны и периодом. Проходит путь от инициации до закрытия или отмены. |
| Отклик | Предложение поставщика по сделке: цена и точка (для парковки — само место). Бывает автоматическим или ручным. |
| Выручка | Доход агента: закрытые сделки в роли поставщика и реферальные начисления. |
| Рейтинг | Автоматический рейтинг системы плюс рейтинг по отзывам (ОВ-11). Считается по паре «роль + сервис» и хранится по дням. |

## Модель данных

В схеме `mp_service` 27 таблиц, 10 представлений и 6 функций (в версии 0.5 было 30 таблиц). Новый сервис описывается только данными: узел в дереве `service`, тексты в `glossary_text`, поля в `service_attribute`, настройки в `service_setting`, включение в пакет в `package_service`.

Типы: **DIM** — справочник, **LIST** — реестр, **LINK** — связка, **FAKT** — события. Общие поля: `date_creation`, `date_start`, `date_end` (`NULL` — бессрочно), `is_active`; порядок — `sort_order`. Нужен PostgreSQL 15 или новее.

| --- | --- | --- | --- | --- |
| **Языки, глоссарий, справочники** |  |  |  |  |

| 2 | icon | DIM | icon_id | Пиктограммы: SVG или ссылка на файл |
| 3 | glossary | DIM | glossary_id | Термин: код и пиктограмма |

| **Сервисы** |  |  |  |  |
| 6 | service | DIM | service_id | Дерево услуг: категория → сервис → вариант |

Группы таблиц и связи между ними (в Claude Docs — схема):

```
Глоссарий и справочники: interface_lang · icon · glossary · glossary_text · dictionary
  (на них ссылаются все таблицы)

Конфигурация сервисов ──► Агенты и подписки ──► Сделки
service, service_setting,  agent, agent_role,      deal, deal_offer,
attribute,                 agent_service,          deal_attribute,
service_attribute,         agent_attribute,        deal_status_log,
service_package,           ui_config,              deal_review,
package_service            agent_subscription,     notification
                           subscription_payment,
                           referral_reward
        │                                             ▲     │
        └── узел дерева, настройки и поля задают сделку ┘     ▼
                                        Рейтинг и санкции: rating_history · agent_sanction
```

Конфигурация сервисов определяет, какие сервисы доступны агенту и какие поля и правила есть у сделки. Для нового сервиса меняются только строки в этой группе и в глоссарии.

| `provider_setting` отдельно от `agent_service` | Объединены в `agent_service` | Одна запись на агента и сервис |
| `fraud_event` и `agent_block` | `agent_sanction` | Предупреждение, понижение и блокировка — одна история |
| `glossary` с составным ключом, ссылки логические | `glossary` (термин и пиктограмма) и `glossary_text` (переводы) | Настоящие внешние ключи; одна пиктограмма на все языки |
| Плоский список сервисов | Дерево `service.parent_service_id`: категория → сервис → вариант | Поиск по дереву, наследование настроек и полей |
| У сделки только свои колонки | `deal_attribute` по `service_attribute.attr_scope` (`profile` / `request` / `offer`) | Такси, грузоперевозки, уборка и другие сервисы получают свои поля без изменения структуры |
| `is_activ`, `rn` | `is_active`, `sort_order` | Решение по ОВ-17 |

Цена обобщения — внешний ключ на `dictionary` не проверяет `dict_type` — закрыта триггером `check_dict_type()` (ОВ-22). Он стоит на 9 таблицах и отклоняет значение не того типа, например статус сделки в поле роли: «agent_role.role_id: значение 11 имеет тип DEAL_STATUS, ожидается ROLE». Денежные и гео-поля сделки остались колонками: по ним строятся подбор, сортировка и отчёты.

| Таблица | Проверяемые поля → тип значения |
| --- | --- |
| service_package, agent_role, rating_history | `role_id` → ROLE |
| deal_review | `to_role_id` → ROLE |
| deal | `deal_status_id` → DEAL_STATUS, `payment_method_id` → PAYMENT_METHOD |
| deal_status_log | `deal_status_id` → DEAL_STATUS, `cancel_reason_id` → CANCEL_REASON |
| referral_reward | `referral_level_id` → REFERRAL_LEVEL |
| notification | `notify_type_id` → NOTIFY_TYPE |
| agent_sanction | `reason_id` → SANCTION_REASON |

## ТОП-10 сервисов и иерархия услуг

Услуги собраны в дерево из трёх уровней: категория → сервис → вариант. Клиент ищет по названию или синониму либо идёт по дереву. Сделка создаётся на варианте, а настройки и поля он наследует от сервиса и категории. Состав списка нужно подтвердить (ОВ-23).

| № | Категория | Сервис | Варианты | Гео | Где оказывается | Цена за | Порядок откликов | Свои поля |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 1 | Транспорт и авто | Парковка | Почасовая, на ночь | точка | у поставщика | час | ближе → рейтинг → дешевле | гос. номер (рядом) |
| 2 | Транспорт и авто | Такси | Эконом, Комфорт | маршрут А → Б | у клиента | км | ближе → рейтинг → дешевле | пассажиры; марка и номер авто; время подачи |
| 3 | Доставка и перевозки | Курьер / доставка | Документы и посылки, продукты | маршрут | у клиента | услугу | рейтинг → дешевле → ближе | адрес; телефон (рядом); время подачи |
| 4 | Доставка и перевозки | Грузоперевозки | Переезд квартиры | маршрут | у клиента | час | рейтинг → дешевле → ближе | вес груза, грузчики, адрес |
| 5 | Дом и ремонт | Разнорабочий | Погрузка и разгрузка | точка | у клиента | час | рейтинг → дешевле → ближе | описание задачи, опыт (от категории) |
| 6 | Дом и ремонт | Мастер на час | Электрик, сантехник | точка | у клиента | услугу | рейтинг → дешевле → ближе | описание задачи, опыт (от категории) |
| 7 | Дом и ремонт | Уборка | Уборка квартиры | точка | у клиента | час | рейтинг → дешевле → ближе | площадь; описание, опыт (от категории) |
| 8 | Красота | Парикмахерская | Мужская, женская стрижка | точка | у поставщика (салон) | услугу | рейтинг → ближе → дешевле | фото работ, опыт (от категории) |
| 9 | Красота | Маникюр | С покрытием | точка | у поставщика | услугу | рейтинг → ближе → дешевле | фото работ, опыт (от категории) |
| 10 | Обучение | Репетитор | Математика, английский | без точки | онлайн | час | рейтинг → дешевле → ближе | тема занятия, опыт |

Поля, общие для категории, заданы один раз на категории: «Описание задачи» для «Дома и ремонта», «Фото работ» для «Красоты». Так же наследуются настройки: у маникюра нет своих строк, всё берётся из категории и платформы.

### Как добавить сервис

1. Термин в `glossary` с пиктограммой и переводы с синонимами в `glossary_text`.
2. Узел в `service` под нужной категорией и, если нужно, варианты.
3. Только отличающиеся настройки в `service_setting`; остальные наследуются.
4. Свои поля в `service_attribute` с областью `profile`, `request` или `offer`.
5. Включение в пакет не нужно, если категория уже в пакете.

Пример: «Эвакуатор» в категории «Транспорт и авто» — это 1 термин, 2 перевода, 1 узел и 3 настройки (`geo_mode = route`, `place_mode = client`, `price_unit = km`). Поля «Гос. номер» и «Марка и цвет авто» уже есть.

### Поиск

`v_service_search` отдаёт название, путь в дереве и пиктограмму на языке агента. Искать можно по названию, по любому уровню пути и по синонимам. На тестовых данных запрос «стрижк» находит Парикмахерскую и оба варианта стрижки, а «газель» — Грузоперевозки по синониму.

```sql
SELECT service_id, node_type, service_path, icon_id
FROM mp_service.v_service_search
WHERE interface_lang_id = :lang AND search_text LIKE '%' || lower(:query) || '%'
ORDER BY service_path;
```

## Настройки сервисов

Параметры сервиса — это строки `service_setting`, а не колонки. Функция `get_setting()` ищет значение от узла вверх по дереву до платформы. У настройки может быть диапазон рейтинга поставщика: так смещение точки зависит от сервиса и рейтинга (ОВ-13).

| Код | Значения | Платформа | Переопределения в тестовых данных |
| --- | --- | --- | --- |
| geo_mode | `point` / `route` / `none` | point | Доставка и перевозки, такси — route; репетитор — none |
| place_mode | `provider` / `client` / `online` | provider | Дом и ремонт, доставка, такси — client; репетитор — online |
| price_unit | `fixed` / `hour` / `km` | fixed | Парковка, дом и ремонт, грузоперевозки, репетитор — hour; такси — km; мастер на час — fixed |
| offer_sort_1..3 | `поле:направление`: distance, rating, price; asc / desc | rating:desc, price:asc, distance:asc | Парковка — distance:asc, rating:desc, price:asc; такси — distance:asc, rating:desc; красота — rating:desc, distance:asc |
| near_radius_m | метры | 300 | Такси — 200. В этом радиусе открываются поля с `show_stage = near` |
| approx_offset_m | метры, по диапазону рейтинга | 0 | Парковка: рейтинг ниже 4,0 — 100 м, 4,0–4,5 — 75 м, от 4,5 — 50 м |
| deal_fee_percent | % от сделки | 0 | — |
| forecast_window_min, forecast_grid_m | минуты, метры | 30, 500 | Парковка — окно 15 мин |
| rating_weight_system, rating_weight_review | доли | 0,5 и 0,5 | — |
| currency | код валюты | KZT | — |
| map_pack_refresh_days | дни | 30 | Как часто приложение обновляет офлайн-карту |

```sql
SELECT mp_service.get_setting(1001, 'price_unit');              -- hour: от сервиса «Парковка»
SELECT mp_service.get_setting(1701, 'offer_sort_1');            -- rating:desc: от категории «Красота»
SELECT mp_service.get_setting(1001, 'approx_offset_m', 4.43);   -- 75: по рейтингу поставщика
```

## Монетизация

Платформа зарабатывает на абонплате за пакеты. Клиенты не платят, поставщик платит 2 000 или 3 500 тг в месяц. Компания платит 5 000 тг за 5 субагентов или 8 000 тг за 10, а каждый следующий субагент стоит 1 200 тг (тестовые значения, ОВ-24).

### Пакеты

| Пакет | Роль | Цена, тг/мес | Субагентов в пакете | Субагент сверх пакета, тг/мес | Пробный период, дней | Категории |
| --- | --- | --- | --- | --- | --- | --- |
| Клиент: бесплатно | Клиент | 0 | — | — | — | Все |
| Поставщик: транспорт и доставка | Поставщик | 2 000 | — | — | 90 | Транспорт и авто; Доставка и перевозки |
| Поставщик: все услуги | Поставщик | 3 500 | — | — | 90 | Все |
| Компания + 5 субагентов | Компания | 5 000 | 5 | 1 200 | 90 | Все |
| Компания + 10 субагентов | Компания | 8 000 | 10 | 1 200 | 90 | Все |

Лимита на число субагентов нет (ОВ-6). Компания с 7 субагентами на пакете «+5» платит 5 000 + 2 × 1 200 = 7 400 тг, на пакете «+10» — 8 000 тг. Расчёт делает `v_subscription_charge`.

### Жизненный цикл подписки

1. Агент выбирает пакет: создаётся пробный период (`is_trial = 1`) на `trial_days` дней. Второй пробный период БД не даст создать.
2. Пробный период закончился без оплаты: сервисы приостанавливаются (`agent_service.is_active = 0`), данные сохраняются.
3. Оплата прошла: запись `paid`, новый платный период, реферальные начисления со статусом `pending`.
4. Оплаченный период закончился: начисления переходят в `accrued` и попадают в доход пригласивших. После выплаты со счёта платформы на карту агента — статус `paid_out` с датой и номером операции выплаты; без даты выплаты БД этот статус не примет.
5. Смена пакета: текущий период закрывается, открывается новый с другим пакетом.
6. Оплата не прошла или возврат до конца периода: статус `failed` или `refund`, начисления — `cancelled`. Сторно не нужно: деньги ещё не начислены.

### Реферальное вознаграждение

С каждой оплаты система поднимается по цепочке приглашений и начисляет 10%, 5% и 2% агентам 1–3 уровня. Начисление становится доступным после окончания оплаченного периода (ОВ-4), а после выплаты на карту агента получает статус «выплачено». Выплата оформляется как оплата рекламных услуг агента (ОВ-5); способ выплаты — ОВ-21.

Пример по цепочке 2 → 3 → 5 на 24.10.2026:

| Оплата, тг | Период | Кто платит | Получатель | Уровень | Начислено, тг | Статус |
| --- | --- | --- | --- | --- | --- | --- |
| 2 000 | сентябрь | Агент 5 | Агент 3 | 1 | 200 | paid_out 05.10 |
| 2 000 | сентябрь | Агент 5 | Агент 2 | 2 | 100 | accrued 30.09 |
| 5 000 | октябрь | Агент 3 (компания) | Агент 2 | 1 | 500 | pending до 31.10 |
| 2 000 | октябрь | Агент 5 | Агент 3 | 1 | 200 | pending до 31.10 |
| 2 000 | октябрь | Агент 5 | Агент 2 | 2 | 100 | pending до 31.10 |

### Отчёты по выручке

Агент видит свои доходы и расходы, компания — то же по субагентам. Доходы: закрытые сделки в роли поставщика и начисленные рефералы. Расходы: закрытые сделки в роли клиента (ОВ-9) и абонплата.

| Отчёт | Кому | Источник | Срез |
| --- | --- | --- | --- |
| Доходы и расходы за период | Агент | `v_agent_finance_daily` | Роль, сервис, источник, направление; сумма и число операций |
| На число | Агент | `v_agent_finance_daily` | Один день |
| Тренд | Агент | `v_agent_finance_daily` + `generate_series` | По дням, нули в пустые дни, накопительный итог |
| По субагентам | Компания | `v_company_finance_daily` | Субагент, роль, период или день, тренд |

Запрос выручки агента по ролям за период:

```sql
SELECT coalesce(r.dict_code, f.source) AS role, f.source, f.direction,
       sum(f.cnt) AS cnt, sum(f.amount) AS amount
FROM mp_service.v_agent_finance_daily f
LEFT JOIN mp_service.dictionary r ON r.dict_id = f.role_id
WHERE f.agent_id = :agent AND f.fin_date BETWEEN :date_from AND :date_to
GROUP BY 1, 2, 3;
```

Запрос тренда по дням:

```sql
SELECT d::date AS day, coalesce(sum(f.amount), 0) AS day_amount,
       sum(coalesce(sum(f.amount), 0)) OVER (ORDER BY d) AS cumulative
FROM generate_series(:date_from::date, :date_to::date, interval '1 day') d
LEFT JOIN mp_service.v_agent_finance_daily f
       ON f.fin_date = d::date AND f.agent_id = :agent AND f.direction = 'income'
GROUP BY d ORDER BY d;
```

Для компании — те же запросы по `v_company_finance_daily` с условием `company_agent_id = :agent` и группировкой по `subagent_id`. На тестовых данных у агента 2 за сентябрь–октябрь доход 1 800 тг со сделок и 100 тг рефералов, расход 4 000 тг абонплаты. Ещё 600 тг рефералов ждут окончания октября.

## Процесс сделки

Сделка проходит пять этапов: от запроса клиента до закрытия по QR-коду. Отменить её можно на любом этапе до закрытия. Сейчас клиент платит поставщику напрямую; оплата через счёт платформы заложена на будущее (ОВ-8).

### Этапы

| Этап | Кто | Действие | Статус |
| --- | --- | --- | --- |
| 1. Инициация | Клиент | Указывает точку (необязательно), период, радиус зоны и минимальный рейтинг поставщика, заполняет поля запроса сервиса. Система показывает прогноз цены (ОВ-10). | INIT → MATCHING |
| 2. Подбор | Система | Находит подходящих поставщиков (условия ниже) и рассылает им запрос. | MATCHING |
| 3. Выбор | Поставщик | Откликается автоматически по своим настройкам или вручную: подтверждает время и цену, нажимает «Откликнуться». | OFFERS |
| 4. Согласование | Клиент | Видит отклики списком и на карте, нажимает «Согласовать», открывает маршрут во внешнем приложении. | AGREED |
| 4а. Контакт | Система | При сближении сторон открывает атрибуты с `show_stage = 'near'`: гос. номер, телефон. | CONTACT |
| 5. Закрытие | Обе стороны | Поставщик показывает QR, клиент сканирует. Обе стороны обязательно ставят баллы. | CLOSED |

### Условия подбора поставщика

Поставщик видит сделку, только если выполнены все условия:

1. Его зона пересекается с зоной клиента.
2. Период сделки попадает в его рабочее время (если задано).
3. Прогноз цены пересекается с его диапазоном `price_min..price_max` (если задан).
4. Рейтинг поставщика не ниже `deal.provider_rating_min`.
5. Рейтинг клиента не ниже `agent_service.client_rating_min`.
6. У поставщика активная подписка с этим сервисом, и он не заблокирован.

Автоматический отклик срабатывает при `is_auto = 1` и выполненных условиях 2 и 3.

### Цена

- Прогноз `price_forecast_min..max` зависит от спроса и предложения в зоне. Параметры (`forecast_window_min`, `forecast_grid_m`) заданы в настройках сервиса, сам алгоритм — следующий этап (ОВ-10).
- Цена поставщика индивидуальна: зависит от локации, спроса и его рейтинга. Единица цены — настройка `price_unit`: услуга, час или км.
- Итог для клиента равен цене поставщика: `deal_fee_percent = 0`. Если сбор включат, он считается процентом от цены поставщика.

### Отмена

| Ситуация | Статус | Последствия |
| --- | --- | --- |
| Любая сторона отменяет до контакта: встречи по гео-меткам не было, контакты не открывались | CANCEL_FREE | Без штрафа, отзыв по желанию |
| Поставщик отменяет после согласования | CANCEL_PROVIDER | Рейтинг поставщика снижается, причина обязательна, клиент получает уведомление и форму баллов |
| Клиент отменяет после согласования | CANCEL_CLIENT | Рейтинг клиента снижается, причина обязательна, поставщик получает уведомление и форму баллов |
| Нет откликов до начала периода | EXPIRED | Без последствий |

## Статусы сделки на схеме

```
Основной путь:  INIT → MATCHING → OFFERS → AGREED → CONTACT → CLOSED (QR отсканирован)
                (клиент создал запрос → поставщик откликнулся → клиент нажал «Согласовать» → стороны сблизились)

Исходы отмены:
  MATCHING, OFFERS        → EXPIRED          нет откликов до начала периода
  любой этап до контакта  → CANCEL_FREE      без штрафа: встречи не было, контакты не открывались
  после согласования      → CANCEL_CLIENT /  рейтинг отменившей стороны снижается,
                            CANCEL_PROVIDER  причина отмены обязательна
```

Основной путь ведёт к закрытию по QR. Отмена до контакта не влияет на рейтинг, отмена после согласования снижает рейтинг отменившей стороны.

## Отклики, карта и маршрут

Клиент видит отклики по парковке от ближнего к дальнему; отклики за пределами его зоны скрыты. Порядок задаётся настройкой для каждого сервиса и меняется без изменения кода.

### Правила

1. Отклик хранит точку предложения; для парковки это само место, для такси — машина.
2. Расстояние до точки клиента считается по прямой функцией `geo_distance_m()`.
3. Отклик выводится, если расстояние не больше радиуса зоны клиента. У сервисов без точки отклик выводится всегда.
4. Порядок задают настройки `offer_sort_1..3` сервиса, категории или платформы; при равенстве раньше тот, кто откликнулся первым.
5. Рейтинг в списке — последний `total_rating` поставщика по сервису на дату сделки.
6. Агент показывается псевдонимом; имя открывается после согласования (ОВ-18).
7. До согласования точка смещена на `approx_offset_m`: для парковки 100 м при рейтинге ниже 4,0, 75 м при 4,0–4,5 и 50 м от 4,5. Направление смещения постоянное для отклика, расстояние округлено до 10 м. Точная точка — после согласования выбранного отклика (ОВ-13).

| Сервис | Ключ 1 | Ключ 2 | Ключ 3 |
| --- | --- | --- | --- |
| Парковка | Расстояние, по возрастанию | Рейтинг, по убыванию | Цена, по возрастанию |
| Доставка | Рейтинг, по убыванию | Цена, по возрастанию | Расстояние, по возрастанию |

### Кейс A/B/C/D

Клиент ищет парковку в точке A в радиусе 100 м (сделка 6 в тестовых данных). На тестовой БД список выходит именно в таком порядке:

| Позиция | Агент | Псевдоним | Рейтинг | Стоимость, тг | Точка | Расстояние от A, м |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | Агент 2 | Петр_Парковка | 4,43 | 1 000 | B | 30 |
| 2 | Агент 4 | ErlanPark | 3,95 | 1 100 | D | 50 |
| 3 | Агент 5 | Айгерим | 4,65 | 900 | C | 70 |
| — | Агент 6 | ViktorK | 3,00 | 950 | E | 130, вне зоны, не выводится |

У агента 5 лучшие рейтинг и цена, но для парковки главное — близость, поэтому он третий. Если поставить рейтинг первым ключом, порядок станет 5 → 2 → 4. Пока клиент не согласовал отклик, точки B, D и C показаны со смещением 75, 100 и 50 м — по рейтингу поставщика.

### Карта в приложении

- Подложка — офлайн-пакет карты на данных OpenStreetMap, без ключей (ОВ-14, ОВ-20). Платформа собирает пакет для города из данных OSM (растровый MBTiles — его читает osmdroid в приложении) и раздаёт со своего CDN. Приложение скачивает его на устройство один раз и обновляет раз в `map_pack_refresh_days` = 30 дней, поэтому нагрузка на сервер карт не растёт с числом пользователей.
- В справочнике это запись `MAP_BASE_LAYER` / `OSM_OFFLINE_ALMATY`: ссылка на пакет и версия (202610). Новый город или версия — новая строка. Адрес CDN в тестовых данных — заглушка.
- Тайлы tile.openstreetmap.org (запись `OSM`) — только для тестов: массовая предзагрузка с этого сервера запрещена его политикой.
- На карте обязательна подпись «© участники OpenStreetMap».
- На карте точка клиента, круг его зоны и точки откликов с подписью, например «Петр_Парковка · ★ 4.43 · 1000 тг».
- Нажатие на точку открывает тот же отклик, что и в списке.
- До согласования точки смещены (правило 7).

### Ссылки на маршрут

Маршрут приложение не строит: после согласования клиент нажимает кнопку и переходит во внешнее приложение (ОВ-19). Шаблоны ссылок — записи `dictionary` типа `MAP_ROUTE_LINK`: `{from_*}` — точка клиента, `{to_*}` — точная точка предложения. До согласования `v_deal_offer_route` ссылок не отдаёт.

| Сервис | Шаблон ссылки | Порядок координат |
| --- | --- | --- |
| Яндекс Карты | `https://yandex.kz/maps/?rtext={from_lat},{from_lon}~{to_lat},{to_lon}&rtt=auto` | широта, долгота |
| 2ГИС | `https://2gis.kz/directions/points/{from_lon},{from_lat}%7C{to_lon},{to_lat}` | долгота, широта |
| Google Maps | `https://www.google.com/maps/dir/?api=1&origin={from_lat},{from_lon}&destination={to_lat},{to_lon}&travelmode=driving` | широта, долгота |

Все три шаблона проверены в браузере 24.10.2026 на точках A → B: каждый сервис строит маршрут. На телефоне ссылка открывается в приложении карт, если оно установлено, иначе в браузере.

## Рейтинг и антифрод

Итоговый рейтинг складывается из автоматического рейтинга системы и рейтинга по отзывам (формула — ОВ-11). За повторный фрод агент сначала теряет рейтинг, потом блокируется на неделю, месяц и год.

### Рейтинг

| Составляющая | Источник | Факторы |
| --- | --- | --- |
| system_rating | Расчёт системы | Число закрытых сделок, доля отмен, фрод |
| review_rating | deal_review | Средний балл отзывов, можно с весом по давности |
| total_rating | Формула | 0,5 × system_rating + 0,5 × review_rating; веса — настройки rating_weight_system и rating_weight_review |

### Антифрод

| Шаг | Условие | Действие |
| --- | --- | --- |
| 1 | Первый эпизод: обход платформы — встреча по гео-меткам без закрытой сделки или отмена после показа гос. номеров в радиусе 300 м (ОВ-12) или накрутка рефералов (фиктивные аккаунты с одного устройства, карты или номера) | Предупреждение о понижении рейтинга |
| 2 | Повтор | Понижение system_rating и предупреждение о блокировке |
| 3 | Больше двух эпизодов плюс подозрительно положительные отзывы или недополученная выручка больше принесённой | Блокировка на неделю |
| 4 | Повтор после блокировки | Блокировка на месяц |
| 5 | Ещё один повтор | Блокировка на год |

Все санкции пишутся в `agent_sanction`: причина из справочника (`SANCTION_REASON`), действие и для блокировки — уровень и период. Реферальные начисления от фиктивных аккаунтов переводятся в `cancelled`.

## Тестовые данные и SQL-скрипт

Скрипт `mp_service.sql` создаёт схему `mp_service` и заполняет её тестовыми данными. 24.10.2026 он загружен в PostgreSQL 17 без ошибок: 27 таблиц, 10 представлений, 6 функций и 9 триггеров проверки справочника. Нужен PostgreSQL 15 или новее. Скрипт сначала удаляет схему (`DROP SCHEMA IF EXISTS mp_service CASCADE`), поэтому его нельзя запускать на базе с рабочими данными.

```bash
psql -d <база> -v ON_ERROR_STOP=1 -f mp_service.sql
```
