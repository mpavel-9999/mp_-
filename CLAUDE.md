## Структура

- `graphify-out/` — граф знаний проекта (graphify); что в него не попадает — `.graphifyignore`.
- `tools/backup/hourly_backup.ps1` — ежечасный срез (раздел «Бэкап и продолжение после обрыва»).
- `project_osm_map/` — проект; инструкция запуска — `project_osm_map/README.md`.
  - `app/` — Android, Jetpack Compose, Material 3, osmdroid (без ключей API):
    `core/` (сеть, конфигурация с кэшем по контрольной сумме, тема из палитры, тексты, SVG, время, маршрут, уведомления),
    `data/` (модели и репозитории API v0.7),
    `feature/` (login, home, request, deal, deals, review, settings, profile),
    `ui/` (карта, общие элементы, раскладки шаблонов `template/a|b|c`).
    AGP 9.4.0, Gradle 9.8.2, compileSdk/targetSdk 37, minSdk 24, Kotlin встроенный в AGP 9 — версия поднята
    до 2.4.21 в `buildscript` корневого `build.gradle.kts` (встроенный 2.2.10 не читает текущие библиотеки).
  - `server/` — локальный API на Java (HttpServer + JDBC + GraphHopper) над схемой `mp_service`, 39 методов,
    описание — `server/openapi.yaml`.
  - `db/mp_service.sql` — схема и тестовые данные (пересоздаёт схему целиком); тесты — `db/tests/*.sql`.
  - `docs/v0.7/plans/` — планы этапов с итогами и снимками экранов (`E<n>_screens/`).
  - `docs/TZ_marketplace.md` — ТЗ маркетплейса v0.6 (основной документ — в Claude Docs; актуальная версия — `docs/v0.7/`).

## Договорённости

- Общаемся на русском; коммиты — короткие сообщения на русском. В GitHub не отправлять без просьбы владельца.
- Сообщать, когда нужен ответ владельца.
- Сначала план, потом выполнение. Перед каждым этапом или крупной доработкой — детальный план (шаги, файлы и
  объекты, порядок, критерии проверки), проверка на логическую связанность (каждый шаг опирается только на
  сделанное, нет противоречий с алгоритмом и ТЗ v0.7, ничего не пропущено), согласование с владельцем.
  План сохранять в `project_osm_map/docs/v0.7/plans/`.
- Ход выполнения этапа — в файле плана, раздел «Ход выполнения»: после каждого шага отметка «шаг, дата,
  результат проверки» и обновление блока «Сейчас» в этом файле. Итог этапа — раздел «Итог» в плане.
- Сохранность работы:
  1. После каждого шага плана, проверка которого прошла, — локальный коммит (сообщение «Э<n> шаг <k>: …»).
  2. Перед долгой или рискованной операцией (перезагрузка БД, массовая правка, импорт) — коммит или ручной срез:
     `powershell -NoProfile -ExecutionPolicy Bypass -File tools\backup\hourly_backup.ps1`.
  3. Граф `graphify-out/` обновлять в конце этапа и коммитить вместе с этим файлом; в конце дня с доработками —
     версия графа и синхронизация с Git.
  4. Запас токенов и времени сессии — коммитить заранее, а не когда сессия уже обрывается. Проверка — инструмент
     `get_usage` (контекст сессии и лимиты тарифа): в начале этапа, перед долгой операцией и примерно каждые
     10 шагов работы.
     - Контекст ≥ 70 % — коммит после каждого шага, «Сейчас» всегда актуален.
     - Контекст ≥ 85 % — новых крупных шагов не начинать: довести текущий, коммит, обновить «Сейчас» и
       предложить владельцу продолжить в новой сессии (на 97 % контекст сжимается автоматически и детали теряются).
     - Лимит тарифа на 5 часов ≥ 80 % или недельный ≥ 90 % — коммит и «Сейчас» сразу, предупредить владельца,
       сколько осталось до обнуления.
- Экономия токенов (решение владельца 2026-10-26):
  1. **Одна сессия — один этап.** Этап закрыт (итог, коммит, «Сейчас») — предложить владельцу продолжить следующий
     этап в новой сессии; контекст новой сессии — этот файл, план этапа и граф, а не история прошлой беседы.
  2. **Меньше снимков экрана.** Проверять через API и SQL, где можно; снимок — только когда без глаз не проверить
     (раскладка, подписи, карта) и для отчёта в `E<n>_screens/`. Снимать уменьшенно (≈ ⅓ размера) или фрагментом.
  3. **Короткие ответы.** В чат — итог в 3–5 строк и нужное решение владельца; подробности — в план этапа
     («Ход выполнения»), а не в чат.
  4. **Меньше чтения файлов.** Сначала граф: `graphify query "…" --budget 2000` — где объект и с чем связан;
     затем читать только нужный фрагмент (`offset` / `limit`, `Grep`), не файл целиком; вывод команд — с фильтром.
  5. **Перед закрытием сессии — граф полон.** Обновить граф по изменённым файлам (`/graphify . --update`) и проверить:
     в нём есть все изменённые в сессии исходники, `db/mp_service.sql`, `server/openapi.yaml`, план этапа и этот файл
     (ничего нужного не закрыто `.graphifyignore`); контрольный запрос
     `graphify query "на каком этапе и шаге остановились, что следующее" --budget 3000` отвечает по текущему
     состоянию. Граф коммитить вместе с этим файлом.
- Следить за ресурсами системы, чтобы не положить компьютер (ЦП 14 потоков, ОЗУ 31,5 ГБ, диск C: ~460 ГБ):
  1. Перед тяжёлыми действиями (эмуляторы, сервер с графом дорог — 1–2 ГБ, сборки Gradle, импорт OSM,
     скачивание) проверить ЦП, свободную ОЗУ и место на диске (PowerShell: `Win32_OperatingSystem`,
     `Win32_Processor`, `Get-PSDrive`). Пороги: свободно ОЗУ не меньше 6 ГБ, на C: не меньше 20 ГБ,
     ЦП в покое ниже 80 %. Если меньше — сначала освободить ресурсы или спросить владельца.
  2. После работы останавливать свои процессы: сервер API (java), эмуляторы, демоны Gradle и Kotlin
     (`gradlew --stop`). Остановка фоновой задачи `gradlew :server:run` java не гасит — проверять порт 8080
     и завершать процесс по PID.
  3. Не запускать параллельно несколько тяжёлых задач (две сборки, сборка + импорт графа и т.п.).
  4. Временные файлы (пробные сборки, кэши) удалять после проверки; на диск D: (8 ГБ) ничего не писать.
- Работа с БД:
  1. При создании таблиц, представлений, материализованных представлений — описание объекта и всех его полей
     (`COMMENT ON TABLE / VIEW / MATERIALIZED VIEW`, `COMMENT ON COLUMN`, в том числе для полей представлений).
     Проверка после загрузки: запрос по `pg_attribute` для `relkind IN ('r','v','m')` не находит объектов и полей без описания.
  2. Процедуры и функции — `COMMENT ON FUNCTION / PROCEDURE`, а в теле — комментарий: что выполняет и методика.
- Правила сделки — в БД; приложение показывает действия из `Deal.actions` и ничего не решает само.
- Тексты интерфейса — из глоссария БД (`ui.*`, ошибки — `ui.err.<код>`); кириллицы в строковых литералах
  `feature/` и `ui/` нет. Одна логика экрана — три раскладки по шаблону.

| Что | Значение |
| --- | --- |
| Java для Gradle и сервера | `JAVA_HOME="C:\Program Files\Android\Android Studio\jbr"` (java в PATH нет) |
| Python | `~/.local/bin/python3.15.exe` (`python` в PATH — заглушка Windows Store); для pyyaml/PIL — `C:\ProgramData\anaconda3\python.exe` |
| PostgreSQL 17.6 | `localhost:5432`, база `postgres`, схема `mp_service`; `C:\Program Files\PostgreSQL\17\bin\psql.exe` |
| Android SDK | `C:\Users\User\AppData\Local\Android\Sdk` (`emulator\emulator.exe`, `platform-tools\adb.exe`) |
| Доступ к БД | Пароль и host БД не хранятся нигде (ни в файлах, ни в переменных Windows): когда нужны — **запросить у владельца** и передавать только в переменные окружения запускаемой команды. Поэтому ежечасный срез сохраняет файлы, но не дамп БД — перед рискованной операцией с БД запросить пароль и сделать дамп вручную |
| Переменные | `MP_DB_PASSWORD` — пароль БД (обязательна для сервера, нужна для дампа в бэкапе); `MP_GEO_SECRET` — секрет смещения точек; `MP_DEV_LOGIN=1` — вход по `agent_id` и список агентов; `MP_TEST_PASSWORD` — общий пароль `user_testing_1…5` для HTTP-теста. Пароли — только в переменных, не в файлах и не в Git |
| Данные OSM | `server/data/kazakhstan-latest.osm.pbf` (214 МБ) и кэш `server/data/gh-cache` (в `.gitignore`) |

Команды (из `project_osm_map/`):

- БД с нуля: `psql -h localhost -U postgres -d postgres -v ON_ERROR_STOP=1 -f db/mp_service.sql`.
- Сервер: `$env:MP_DB_PASSWORD=…; $env:MP_GEO_SECRET=…; $env:MP_DEV_LOGIN='1'; .\gradlew.bat :server:run`;
  готовность — `GET http://127.0.0.1:8080/api/health` → `"routing":"готов"`. Перезапуск сервера сбрасывает токены
  (в памяти) — приложение получит 401 и вернётся на вход.
- Эмуляторы: `emulator -avd Medium_Phone_API_37.0 -port 5554` (клиент, `user_testing_1` / агент 7) и
  `emulator -avd Medium_Phone_B -port 5556` (поставщик, `user_testing_2` / агент 8); для каждого
  `adb -s emulator-555x reverse tcp:8080 tcp:8080` (адрес 10.0.2.2 при targetSdk 37 закрыт). Часовой пояс
  эмулятора выставлять не нужно (с Э5 шаг 1 приложение считает время по Алматы, Р-4); при желании —
  `adb -s emulator-555x shell cmd alarm set-timezone Asia/Almaty`.
- Приложение: `$env:ANDROID_SERIAL='emulator-5554'; .\gradlew.bat :app:installDebug`.
- Тесты: SQL — `psql … -f db/tests/01_rules.sql`, `02_cancel_mode.sql`, `03_period.sql` (на свежезагруженной БД:
  опираются на кейс A/B/C/D); HTTP — `MP_TEST_PASSWORD=… python server/tests/api_smoke.py` (сервер запущен);
  приложение — `.\gradlew.bat :app:testDebugUnitTest`; сборка — `:app:assembleDebug`, `:server:build`.
- Особенности: adb из Git Bash — `MSYS_NO_PATHCONV=1` (иначе пути `/sdcard/…` портятся); кириллицу через
  `adb shell input text` не ввести — в проверках латиница и цифры; Material-диалоги даты — на языке устройства.

## Бэкап и продолжение после обрыва

- Ежечасный срез: задача Планировщика Windows `github_repo hourly backup` запускает `tools/backup/hourly_backup.ps1`
  (только пока владелец вошёл в Windows). Срезы — `C:\MP\Backups\github_repo\<ГГГГММДД-ЧЧмм>\`, журнал — `backup.log` там же.
  - `repo.bundle` — ветки и срез рабочей копии с незакоммиченными и новыми файлами (ссылка `refs/backup/<время>`;
    ветка, индекс и рабочая копия не меняются, в GitHub ничего не уходит);
  - `mp_service.sql` — дамп схемы БД, только если пароль задан в `MP_DB_PASSWORD` / `PGPASSWORD` или `pgpass.conf`;
  - `info.txt` — ветка, HEAD, незакоммиченные изменения. Без изменений новый срез не создаётся;
    хранится 48 ч, первый срез дня — 14 дней; при свободном месте на C: меньше 20 ГБ срез пропускается.
- Восстановление файлов из среза (в своей копии): `git switch -c restore-<время> refs/backup/<время>`
  или выборочно `git restore --source=refs/backup/<время> -- <путь>`.
- Если `.git` потерян: `git init restored`, затем в нём
  `git fetch <папка среза>\repo.bundle "refs/heads/*:refs/heads/*" "refs/backup/<время>:refs/heads/restore"` и `git switch restore`.
- БД из среза: `psql -h localhost -U postgres -d postgres -v ON_ERROR_STOP=1 -f <папка среза>\mp_service.sql`.
- Начало сессии после обрыва:
  1. Прочитать «Сейчас» и «Открытые вопросы»; `git status`, `git log -3`; последние строки `backup.log`.
  2. Открыть план текущего этапа, раздел «Ход выполнения» — продолжить со следующего неотмеченного шага.
     Незакоммиченные изменения сверить с последним срезом (`info.txt`).
  3. Спросить граф: `graphify query "на каком этапе и шаге остановились, что следующее" --budget 3000`.
  4. Остановить оставшиеся процессы (java на порту 8080, эмуляторы) и проверить ресурсы.
